TradeReady API

Read-only access to your own data, for the tools you already use

The TradeReady API lets your bookkeeping software, a spreadsheet script or an automation tool read your customers, jobs, estimates, invoices, payments, expenses and mileage. You create a key in the app, choose what it can read, and give it to the tool. The API is read-only: nothing can create, change or delete your data through it.

Get a key

  1. In the TradeReady app, open Settings → API access. You need to be signed in and online.
  2. Tap Create key, give it a name you'll recognize (for example “QuickBooks sync”), choose what it can read, and pick when it expires: in 1 year (the default), in 90 days, or never.
  3. Copy the key and paste it into your tool straight away. TradeReady shows a key once and can't show it again, because we only keep a fingerprint of it, never the key itself.

You can have up to 5 active keys. Each key's row in the app shows when it was last used, and Recent activity lists its latest requests. Revoking a key stops it on the very next request. Rotating a key gives you a new key with the same name and scopes; the old key keeps working for 24 hours (or stops immediately, if you choose) so you have time to update your tool.

Keys look like trk_ followed by 107 letters, digits, - and _. Every example on this page uses a placeholder, never a real key.

Authentication

Send the key in the Authorization header on every request:

Authorization: Bearer trk_your_key_here
  • Never put a key in a URL. A request with a key in its query string is refused with key_in_query. URLs end up in logs and browser history, so treat a key that was ever sent in a URL as exposed: revoke it and create a new one.
  • Keys are for servers and scripts, not web pages. The API sends no CORS headers, so a browser page can't read its responses. Keep keys in your tool's secret settings or an environment variable.
  • Only GET is accepted. Any other method gets 405 method_not_allowed.

Scopes

A key can only read what you allowed when you created it.

ScopeLets the key read
customers:read/v1/customers
jobs:read/v1/jobs and /v1/estimates
invoices:read/v1/invoices and /v1/payments
expenses:read/v1/expenses
mileage:read/v1/mileage

The app offers two presets: Everything (all five) and Bookkeeping (customers, invoices, expenses and mileage). /v1/account works with any scope. Reading something outside the key's scopes returns 403 insufficient_scope.

Base URL and first request

Every endpoint lives under one base URL:

https://tradeready-backend.tradeready.workers.dev

Check that your key works:

export TRADEREADY_API_KEY="trk_your_key_here"

curl https://tradeready-backend.tradeready.workers.dev/v1/account \
  -H "Authorization: Bearer $TRADEREADY_API_KEY"
{
  "data": {
    "businessName": "Ruiz Electric",
    "currency": "USD",
    "dataAsOf": "2026-10-03T17:42:10.512Z",
    "apiVersion": "2026-10-03",
    "key": { "id": "6f1c…", "name": "QuickBooks sync", "prefix": "trk_Ab3dE9fQ", "scopes": ["invoices:read"], "expiresAt": "2027-10-03T17:00:00.000Z" }
  }
}

A machine-readable description of every endpoint and field is at /v1/openapi.json (OpenAPI 3.1, no key needed).

Conventions

  • Money is a JSON number in US dollars, rounded to cents.
  • Business dates (due dates, job dates, expense dates) are returned exactly as entered, usually YYYY-MM-DD, and are never shifted between time zones.
  • updatedAt and other server times are ISO-8601 in UTC.
  • Every object always has the same fields. A value that isn't set is null, never missing.
  • Archived records are included, with archivedAt set.

Pagination

List endpoints return one page at a time, oldest change first:

GET /v1/invoices?limit=100
{
  "data": [ … up to 100 invoices … ],
  "nextCursor": "eyJ1Ijoi…",
  "dataAsOf": "2026-10-03T17:42:10.512Z",
  "nextUpdatedSince": "2026-10-03T17:40:05.120Z"
}
  • limit is 1 to 100 (default 50).
  • Pass nextCursor back as cursor to get the next page. When nextCursor is null, you have everything. Cursors are opaque; don't build or edit them.
  • Records are ordered by updatedAt, then id, so a page never shifts under you while you read.
  • A single record is GET /v1/{resource}/{id} and returns {"data": {…}, "dataAsOf": …}. A record that doesn't exist, was deleted, or isn't yours is 404 not_found.
  • Payments are paged by invoice: one page holds the payments of up to limit invoices, so a page can hold any number of payments, including none. Keep following nextCursor.
  • Unknown query parameters are refused with 400 invalid_parameter, so a typo never silently returns everything.

Incremental sync

To keep another system up to date, read everything once, then ask only for what changed:

  1. First run: page through /v1/invoices with no updated_since. Save each record by its id.
  2. When the last page arrives (nextCursor is null), store its nextUpdatedSince.
  3. Next run: send updated_since=<the value you stored> and page through again. Store the new nextUpdatedSince when you finish. If nothing changed it is null: keep your old value.

nextUpdatedSince deliberately overlaps the previous run by 5 seconds, so a change saved at the same moment as your last request is never missed. You may see a record twice; save by id and the duplicate is harmless.

Deleted records

With updated_since, records deleted since then come back as tombstones, so you can remove them too:

{ "id": "inv1727992000000", "deleted": true, "updatedAt": "2026-10-03T16:02:41.000Z" }

Without updated_since, deleted records are left out.

Worked example (Node.js 18 or later)

const BASE = "https://tradeready-backend.tradeready.workers.dev";
const headers = { Authorization: `Bearer ${process.env.TRADEREADY_API_KEY}` };

// store: your own storage, e.g. a database table keyed by id.
async function syncInvoices(store) {
  const since = await store.getWatermark("invoices"); // null on the first run
  let cursor = null;
  let watermark = null;
  for (;;) {
    const url = new URL("/v1/invoices", BASE);
    url.searchParams.set("limit", "100");
    if (since) url.searchParams.set("updated_since", since);
    if (cursor) url.searchParams.set("cursor", cursor);

    const res = await fetch(url, { headers });
    if (res.status === 429) {
      const wait = Number(res.headers.get("Retry-After") || 60);
      await new Promise((r) => setTimeout(r, wait * 1000));
      continue; // same page again
    }
    const body = await res.json();
    if (!res.ok) throw new Error(`${res.status} ${body.error.code}: ${body.error.message}`);

    for (const item of body.data) {
      if (item.deleted) await store.remove(item.id);
      else await store.upsert(item.id, item);
    }
    watermark = body.nextUpdatedSince ?? watermark;
    if (!body.nextCursor) break;
    cursor = body.nextCursor;
  }
  if (watermark) await store.setWatermark("invoices", watermark);
}

How fresh the data is

The API shows the cloud copy of your data as of your phone's last sync. TradeReady works offline; anything you change on a device reaches the API after that device syncs.

Every response includes dataAsOf: the newest change the cloud has for that kind of record (or, on /v1/account, across everything the key can read). If it is older than you expect, open the app on the phone you used and let it sync.

Rate limits

LimitApplies to
60 requests per minuteeach key
5,000 requests per dayeach key (days are UTC)
10,000 requests per dayall of your keys together

Responses carry X-RateLimit-Limit, X-RateLimit-Remaining and X-RateLimit-Reset (Unix time, in seconds, when the current minute's allowance resets). Over a limit, you get 429 rate_limited with a Retry-After header in seconds; wait that long and try again. Requests that are refused don't use up your allowance. Polling every 15 minutes across all seven lists uses fewer than 700 requests a day.

Repeated requests with bad keys from one address are slowed down too.

Versioning

  • The version is in the path: /v1. Within /v1 we only add things: new endpoints, new fields and new values for fields like status. Write your code so an unfamiliar field or value doesn't break it.
  • A change that could break existing code ships as /v2, and /v1 keeps working for at least 6 months after that. During that time /v1 responses carry Deprecation and Sunset headers.
  • Every response has a TradeReady-Api-Version header with the date of the last addition, for your logs.

Zapier and other tools

Any tool that can send a GET request with a custom header can use the API. In Zapier, use Webhooks by Zapier to poll a list endpoint, such as https://tradeready-backend.tradeready.workers.dev/v1/invoices?limit=100, with the header Authorization: Bearer <your key>, and use id to tell records apart. There is no listed TradeReady app in Zapier yet, and the API does not send webhooks; poll instead, no more often than you need.

Security and privacy

  • Anyone who has a key can read the kinds of data you chose for it, until it expires or you revoke it. Only give keys to services you trust, and give each service its own key so you can revoke one without the others.
  • TradeReady stores only a one-way fingerprint of each key, so a key can't be recovered from our systems.
  • We log each API request (time, key, endpoint and IP address) for 90 days for security, and show recent activity to you in the app. We never log the key itself or the details of your query.
  • Deleting your TradeReady account deletes every key and its activity log with it.
  • See our Privacy Policy and Terms of Service. Questions or a security concern: support@gettradereadyapp.com. Please never email us a key.
